# TextLink Huffman 壓縮率分析報告

## 1. 分析目的與測試資料

### 1.1 分析目的

本研究針對 TextLink 專案實作的 Huffman 壓縮功能進行測試與分析，主要目的如下：

1. 比較 RAW（不壓縮）與 HUFF（Huffman 壓縮）模式的資料傳輸量及執行時間。
2. 驗證 Huffman 編碼的平均碼長（L）與 Shannon Entropy（H）之間的理論關係。
3. 分析 UTF-8 文字使用 CHAR、BYTE，以及 16-bit PCM WAV 使用 S16、BYTE 作為符號時的壓縮效果。
4. 分析 Bitstream、Codebook、Header 與傳輸協定開銷對最終壓縮比例的影響。
5. 評估短訊息的壓縮效益，並使用簡化模型估計 RAW 與 HUFF 的損益平衡頻寬。

### 1.2 測試資料

本研究使用四份超過 1 MB 的測試檔案：

| 測試檔案 | 檔案類型 | 原始大小（bytes） | 主要特性 |
|---|---|---:|---|
| real_chinese.txt | UTF-8 中文文字 | 1,200,335 | 以中文自然語言為主 |
| real_english.txt | UTF-8 英文文字 | 1,258,581 | 以英文自然語言為主 |
| audio_music_20s.wav | PCM WAV 音訊 | 3,528,044 | 16-bit、雙聲道、44,100 Hz、20 秒 |
| audio_noise.wav | PCM WAV 音訊 | 1,120,044 | 16-bit、單聲道、8,000 Hz、約 70 秒的雜訊 |

### 1.3 測試方式

正式傳輸效能測試包含 localhost（127.0.0.1）及雙實體電腦兩種環境。每種環境針對四份檔案，分別使用 RAW 與 HUFF 模式，每種組合重複五次，各完成 40 次正式量測，合計 80 次。測試結果以五次量測的中位數進行比較。兩種環境的設備及部分測試檔案版本存在差異，因此分別分析其結果。

文字檔的正式 HUFF 傳輸使用 CHAR 模式；WAV 的正式 HUFF 傳輸使用 S16 模式。

另外，為比較不同符號定義，本研究使用 C 語言 `huff_encode()` 額外產生 CHAR/BYTE 及 S16/BYTE 的實際編碼資料，分析 N、K、H、L、Codebook 與 Bitstream 大小。

正式傳輸紀錄儲存於 `benchmarks/formal_raw_40.csv`，壓縮分析結果則儲存於 `benchmarks/figures/`。

## 2. 壓縮比例與計算公式

### 2.1 原始資料大小

以原始檔案的實際位元組數（bytes）作為比較基準，記為 S。

### 2.2 純 Huffman Bitstream 比例

純 Bitstream 比例只考慮 Huffman 編碼後的資料位元流，不包含 Codebook、Header 與其他協定開銷。

`R_bitstream = Bitstream bytes / S × 100%`

Bitstream bytes 包含儲存時最後一個 byte 可能需要的補齊位元。

### 2.3 完整 Huffman 編碼比例

完整 Huffman 編碼包含 Bitstream、Codebook、固定 Header，以及 WAV S16 模式所需保存的額外資料。

`R_encoded = Encoded bytes / S × 100%`

### 2.4 實際上線比例

實際上線比例以網路協定傳送的總 bytes 作為分子。

`R_wire = Wire bytes / S × 100%`

其中 Wire bytes 包含實際編碼資料及 TextLink 傳輸協定所需的額外資料。

RAW 模式雖然不壓縮原始檔案，但因為仍需要傳輸協定標頭與相關控制資料，因此實際上線比例可能略大於 100%。

### 2.5 節省比例

`Saving (%) = (1 − Wire bytes / S) × 100%`

- Saving 大於 0：表示傳輸資料量減少。
- Saving 等於 0：表示與原始資料大小相同。
- Saving 小於 0：表示實際上線資料量比原始檔案更大。

本研究主要使用實際上線比例比較傳輸資料量，並另外使用 Bitstream 與 Encoded 比例分析壓縮格式本身的成本。

## 3. Shannon Entropy（H）與平均碼長（L）

### 3.1 符號總數 N 與不同符號數 K

N 表示輸入資料的符號總數，K 表示不同符號的種類數。

符號的定義會影響 N 與 K，例如：

- BYTE：每個 8-bit byte 為一個符號。
- CHAR：每個完整 UTF-8 字元為一個符號。
- S16：每個 16-bit PCM 音訊 sample 為一個符號。

因此，不同模式的 N、K、H 與 L 不一定可以直接比較。

### 3.2 Shannon Entropy（H）

Shannon Entropy 用來衡量資料來源的平均資訊量：

`H = −Σ p(i) × log₂(p(i))`

其中 p(i) 表示第 i 種符號出現的機率。

H 的單位為 bits/symbol。

### 3.3 Huffman 平均碼長（L）

Huffman 平均碼長是各符號編碼長度依出現機率加權的平均：

`L = Σ p(i) × l(i)`

其中 l(i) 是第 i 種符號的 Huffman code 長度。

L 的單位同樣為 bits/symbol。

對於本次具有兩種以上符號的測試資料，二元 Huffman 編碼滿足：

`H ≤ L < H + 1`

### 3.4 實際分析結果

| 測試資料 | 符號 | N | K | H (bits/symbol) | L (bits/symbol) |
|---|---|---:|---:|---:|---:|
| 中文文字 | CHAR | 403,185 | 373 | 7.6020 | 7.6460 |
| 中文文字 | BYTE | 1,200,335 | 74 | 5.6989 | 5.7300 |
| 英文文字 | CHAR | 1,256,253 | 57 | 4.3054 | 4.3212 |
| 英文文字 | BYTE | 1,258,581 | 59 | 4.3188 | 4.3347 |
| 音樂 WAV | S16 | 1,764,000 | 63,954 | 15.2980 | 15.3296 |
| 音樂 WAV | BYTE | 3,528,044 | 256 | 7.8407 | 7.8676 |
| 雜訊 WAV | S16 | 560,000 | 65,522 | 15.9135 | 15.9445 |
| 雜訊 WAV | BYTE | 1,120,044 | 256 | 7.9998 | 8.0000 |

八組資料均符合 `H ≤ L < H + 1`，顯示實際編碼的平均碼長與 Huffman 理論關係一致。

需要注意的是，H 與 L 只描述每個符號平均所需的 bits，並未包含 Codebook、Header 等額外儲存成本，因此不能直接視為完整檔案的實際壓縮比例。

### 4.4 理論壓縮率、純編碼比例與實際壓縮率比較

為完整比較 Huffman 編碼的理論效益與實際儲存成本，本研究以相同的原始檔案大小作為分母，計算理論壓縮比例、純編碼比例、Codebook 開銷及完整編碼比例。

計算公式：

- 理論壓縮比例 = H × N ÷ 8 ÷ 原始 bytes × 100%
- 純編碼比例 = L × N ÷ 8 ÷ 原始 bytes × 100%
- Codebook 比例 = Codebook bytes ÷ 原始 bytes × 100%
- 實際編碼比例 = Encoded bytes ÷ 原始 bytes × 100%

| 測試資料／符號 | 理論比例 | 純編碼比例 | Codebook 比例 | 實際 Encoded 比例 |
|---|---:|---:|---:|---:|
| 中文文字 CHAR | 31.93% | 32.11% | 0.28% | 32.38% |
| 中文文字 BYTE | 71.24% | 71.63% | 0.04% | 71.66% |
| 英文文字 CHAR | 53.75% | 53.95% | 0.04% | 53.96% |
| 英文文字 BYTE | 53.99% | 54.18% | 0.03% | 54.21% |
| 音樂 WAV S16 | 95.62% | 95.81% | 12.69% | 108.50% |
| 音樂 WAV BYTE | 98.01% | 98.35% | 0.04% | 98.39% |
| 雜訊 WAV S16 | 99.46% | 99.65% | 40.95% | 140.60% |
| 雜訊 WAV BYTE | 100.00% | 100.00% | 0.14% | 100.14% |

由表中可觀察到，純編碼比例通常與 Shannon Entropy 所預測的理論下限相當接近，表示 Huffman 編碼本身具有合理的編碼效率。

中文文字以 UTF-8 字元（CHAR）為符號時，純編碼比例約為 32.11%，加上 Codebook 與 Header 後，實際編碼比例約為 32.38%，額外開銷相對有限。

相較之下，音樂 WAV 與雜訊 WAV 以 16-bit Sample（S16）為符號時，雖然純編碼比例分別約為 95.81% 與 99.65%，但 Codebook 開銷達原始檔案大小的 12.69% 與 40.95%，使完整編碼比例增加至 108.50% 與 140.60%。

因此，**Huffman Bitstream 接近理論最佳碼長，不代表完整檔案就一定能有效壓縮**。符號種類數、Codebook 儲存方式及必要 Header，都是影響實際壓縮率的重要因素。

此外，WAV 的 S16 模式只將 PCM Sample 作為 Huffman 符號，非音訊資料另行保留；BYTE 模式則以整個檔案的 bytes 作為編碼對象。兩種模式應以相同原始檔案大小為基準比較壓縮比例，不宜直接比較不同單位的 H 值。

## 5. 教授指定問題
### 5.1 實際壓縮率與純編碼壓縮率差異

本研究發現，Huffman 的實際壓縮效果除了受到資料熵影響，也與 Codebook 儲存成本及傳輸協定額外開銷有關。中文與英文文字檔具有較小的符號種類數，因此純編碼與實際傳輸比例差距不大；相較之下，16-bit WAV 的符號種類數接近 65,536 種，使 Codebook 佔用大量空間。尤其雜訊 WAV 的平均碼長接近 16 bits/符號，幾乎沒有編碼收益，因此加入 Codebook 後，實際傳輸量反而超過原始檔案大小。

### 5.2 聊天短訊息的 Huffman 壓縮效果

本專案的聊天功能使用 `SYM_CHAR` 作為 Huffman 符號定義，每次傳送訊息都會重新建立並附上獨立 Codebook。當 Huffman 輸出大於原始訊息時，程式仍以 HUFF 模式傳送，不會自動回退 RAW。

為分析短訊息的壓縮效益，本次使用原本的 C Huffman 編碼器，分別針對中文自然語言、英文自然語言以及高度重複的英文字母 A 進行不同長度的離線編碼測試。

傳輸比例計算為：

`HUFF 傳輸比例 = (Huffman encoded bytes + 5) / 原始 UTF-8 bytes × 100%`

其中額外的 5 bytes 為 TextLink Frame Header。

| 字元數 | 中文自然語言 | 英文自然語言 | 重複字元 A |
|---:|---:|---:|---:|
| 10 | 367.86% | 850.00% | 290.00% |
| 50 | 291.67% | 616.00% | 68.00% |
| 100 | 277.55% | 440.00% | 40.00% |
| 500 | 174.70% | 153.20% | 18.00% |
| 1,000 | 113.15% | 106.40% | 15.20% |
| 2,000 | 80.26% | 81.59% | 13.85% |
| 2,500 | 71.77% | 75.96% | 13.60% |


**中文自然語言聊天訊息的實際傳輸量**

| 字元數 | 原始 bytes | RAW 上線 bytes | HUFF 上線 bytes（含 Codebook） | HUFF 壓縮率 |
|---:|---:|---:|---:|---:|
| 10 | 28 | 33 | 103 | 367.86% |
| 50 | 144 | 149 | 420 | 291.67% |
| 100 | 294 | 299 | 816 | 277.55% |
| 500 | 1,486 | 1,491 | 2,596 | 174.70% |
| 1,000 | 2,974 | 2,979 | 3,365 | 113.15% |
| 2,000 | 5,952 | 5,957 | 4,777 | 80.26% |
| 2,500 | 7,442 | 7,447 | 5,341 | 71.77% |

其中 RAW 上線 bytes = 原始 bytes + 5-byte Frame Header；
HUFF 上線 bytes = Huffman encoded bytes + 5-byte Frame Header，
包含 Codebook 與必要編碼資料。

本表使用實際 C Huffman 編碼器進行離線測試，
並依照 TextLink 的 Frame 格式計算上線 bytes，
並非直接擷取 TCP 封包的實測結果。

**結果分析：**

1. 中文與英文自然語言在 1,000 字元時，上線資料量仍大於原始訊息；2,000 字元時則已低於 100%。
2. 高度重複的字元 A，在測試長度達到 50 字元時即觀察到 68% 的傳輸比例，顯示符號種類與分布會顯著影響壓縮效果。
3. 短訊息中 Codebook 與固定標頭占比高，容易抵消 Huffman Bitstream 節省的資料量。
4. 隨訊息長度增加，固定開銷被分攤，壓縮效益通常更明顯，但仍取決於實際文字內容。

**結論：**

TextLink 每則 HUFF 聊天訊息都攜帶獨立 Codebook，因此短訊息容易發生壓縮後資料量增加的現象。在本次測試資料中，中文與英文自然語言於 2,000 字元時已觀察到傳輸比例低於 100%；重複字元 A 則於 50 字元時便達到相同條件。

上述數值只是本次測試長度的觀察結果，不代表所有訊息共用的固定臨界長度。本實驗透過 C 編碼器離線取得資料大小，未實際透過 TCP 傳送，網路 Frame 開銷依 `chat.c` 的傳輸格式計算。

原始分析資料：`benchmarks/figures/chat_compression.csv`。

### 5.3 CHAR 與 BYTE 符號定義對文字壓縮效果的影響

本研究比較 Huffman 採用 UTF-8 字元（CHAR）與單一位元組（BYTE）作為符號時，對中文及英文文字檔所造成的壓縮差異。

在 CHAR 模式下，一個完整 UTF-8 字元視為一個符號；BYTE 模式則將每個 byte 視為獨立符號。因此，兩種模式會產生不同的符號頻率分布、Shannon Entropy（H）、Huffman 平均碼長（L）及 Codebook。

| 指標 | 中文 CHAR | 中文 BYTE | 英文 CHAR | 英文 BYTE |
|---|---:|---:|---:|---:|
| 原始大小 (bytes) | 1,200,335 | 1,200,335 | 1,258,581 | 1,258,581 |
| 符號總數 N | 403,185 | 1,200,335 | 1,256,253 | 1,258,581 |
| 不同符號數 K | 373 | 74 | 57 | 59 |
| H (bits/symbol) | 7.6020 | 5.6989 | 4.3054 | 4.3188 |
| L (bits/symbol) | 7.6460 | 5.7300 | 4.3212 | 4.3347 |
| Codebook (bytes) | 3,357 | 444 | 513 | 354 |
| 實際 encoded bytes | 388,713 | 860,195 | 679,089 | 682,319 |
| 編碼比例 | 32.38% | 71.66% | 53.96% | 54.21% |

**結果分析**

中文文字檔使用 CHAR 模式時，編碼比例為 32.38%，明顯低於 BYTE 模式的 71.66%。這是因為中文 UTF-8 字元通常由多個 bytes 組成，CHAR 模式可以直接將完整中文字視為單一符號進行 Huffman 編碼，更有效利用文字頻率分布。雖然 CHAR 的 Codebook 較大，但節省的 Bitstream 足以抵銷額外成本。

另一方面，英文文字檔的 CHAR 與 BYTE 編碼比例分別為 53.96% 與 54.21%，差距僅約 0.25 個百分點。這是因為英文文章主要由單一 byte 的 ASCII 字元組成，因此兩種模式的符號分布十分接近。

需要注意的是，CHAR 與 BYTE 的熵 H 均以 bits/symbol 表示，但 symbol 的定義不同，不能只比較 H 的數值大小就判斷壓縮效能。實際效果應使用相同原始檔案大小作為基準，比較最終編碼資料量。

**結論**

符號定義會直接影響 Huffman 的壓縮效果。對本次中文自然語言資料而言，CHAR 模式比 BYTE 模式更有效；對以 ASCII 為主的英文文章而言，兩者差異很小。因此，TextLink 對 UTF-8 文字採用 CHAR 模式，符合本次實驗觀察到的壓縮效益。

### 5.4 WAV 音訊採用 S16 與 BYTE 符號定義的比較

本研究針對 16-bit PCM WAV 音訊，比較 Huffman 使用完整 16-bit sample（S16）及單一位元組（BYTE）作為符號時的壓縮效能。

在 S16 模式下，每個 16-bit 音訊 sample 視為一個符號，理論上最多有 65,536 種不同符號；BYTE 模式則以 8-bit byte 為符號，最多只有 256 種不同值。符號定義會影響 Shannon Entropy、Huffman 平均碼長、Bitstream 大小，以及 Codebook 的儲存成本。

| 指標 | 音樂 S16 | 音樂 BYTE | 雜訊 S16 | 雜訊 BYTE |
|---|---:|---:|---:|---:|
| 原始檔案 (bytes) | 3,528,044 | 3,528,044 | 1,120,044 | 1,120,044 |
| 符號總數 N | 1,764,000 | 3,528,044 | 560,000 | 1,120,044 |
| 不同符號數 K | 63,954 | 256 | 65,522 | 256 |
| H (bits/symbol) | 15.2980 | 7.8407 | 15.9135 | 7.9998 |
| L (bits/symbol) | 15.3296 | 7.8676 | 15.9445 | 8.0000 |
| Codebook (bytes) | 447,678 | 1,536 | 458,654 | 1,536 |
| Bitstream (bytes) | 3,380,184 | 3,469,654 | 1,116,112 | 1,120,044 |
| 實際 encoded bytes | 3,827,927 | 3,471,203 | 1,574,831 | 1,121,593 |
| 編碼比例 | 108.50% | 98.39% | 140.60% | 100.14% |

**結果分析**

在音樂 WAV 的測試中，S16 模式所產生的 Bitstream 為 3,380,184 bytes，比 BYTE 模式的 3,469,654 bytes 更小。然而，S16 模式包含 63,954 種不同符號，Codebook 達到 447,678 bytes，遠大於 BYTE 模式的 1,536 bytes，因此完整編碼比例反而增加至 108.50%。相比之下，BYTE 模式為 98.39%，略低於原始檔案大小。

在雜訊 WAV 的測試中，S16 模式的符號種類高達 65,522 種，Shannon Entropy 為 15.9135 bits/symbol，非常接近 16-bit 符號的最大熵。由於雜訊的符號分布接近均勻，Huffman 難以縮短平均碼長，S16 模式的 L 達到 15.9445 bits/symbol。加上 458,654 bytes 的 Codebook 後，實際編碼比例高達 140.60%。

雜訊採用 BYTE 模式時，熵也接近 8 bits/symbol，平均碼長為 8 bits/symbol，幾乎沒有 Bitstream 壓縮效益，但由於 Codebook 僅 1,536 bytes，最終編碼比例約為 100.14%，資料量增加程度明顯小於 S16。

本次 S16 與 BYTE 的分析對象略有差異：S16 將 PCM sample 作為 Huffman 符號，並另存 WAV 的非音訊資料；BYTE 則直接編碼整個 WAV 檔案的所有 bytes。因此比較時應以相同的原始檔案大小作為分母，而不能直接比較不同符號定義下的 H 數值。

**結論**

較大的 Huffman 符號並不保證較好的整體壓縮率。雖然 S16 可能產生較小的 Bitstream，但其符號種類數多、Codebook 儲存成本高，可能使最終 encoded bytes 超過原始檔案。對本次測試的音樂 WAV 與雜訊 WAV 而言，BYTE 模式的整體壓縮效果均優於 S16 模式。

因此，評估 Huffman 壓縮效能時，不能僅比較熵 H 或 Bitstream 大小，也必須計入 Codebook、固定 Header 與其他必要資料。

## 6. RAW 與 Huffman 傳輸效能分析

本研究使用四份正式測試檔案，分別以 RAW 與 HUFF 模式進行檔案傳輸，每種組合重複量測五次，共取得 40 次測試結果。為降低單次測量波動的影響，本研究使用送出端 `total_ms` 的中位數進行比較。

測試環境為同一台電腦的 localhost（127.0.0.1），因此結果主要反映本機程式處理及傳輸成本，不代表跨電腦網路的實際表現。

| 測試檔案 | RAW total_ms | HUFF total_ms | 時間差 |
|---|---:|---:|---:|
| 中文文章 | 35.0 ms | 51.8 ms | +16.8 ms |
| 英文文章 | 37.1 ms | 85.0 ms | +47.9 ms |
| 音樂 WAV | 92.8 ms | 389.1 ms | +296.3 ms |
| 雜訊 WAV | 34.0 ms | 162.5 ms | +128.5 ms |

### 6.1 結果分析

在 localhost 測試中，四份檔案的 HUFF 送出端總時間均高於 RAW。這表示在本次測試條件下，Huffman 壓縮所涉及的額外處理與傳輸流程成本，未能被傳輸資料量減少的收益抵銷。

對於中文與英文文章，HUFF 模式能顯著減少實際傳輸 bytes，但仍需要執行符號頻率統計、Huffman Tree 建立、Codebook 序列化及 Bitstream 編碼等操作。

對於音樂 WAV 與雜訊 WAV，S16 模式具有大量不同符號，Codebook 儲存成本高，且最終編碼資料量超過原始檔案。因此，在本次測試中，HUFF 不僅未減少傳輸資料量，送出端總時間也較長。

### 6.2 測試限制

本次效能數據來自 localhost，不包含一般跨電腦網路可能出現的頻寬限制、封包遺失、網路壅塞及其他變動因素。

此外，送出端 `total_ms` 是整體量測結果，不能直接視為 Huffman 編碼時間；接收端的 `total_ms` 也不能直接與送出端結果相加。

### 6.3 結論

壓縮率與傳輸速度是兩種不同的評估指標。Huffman 可以降低資料量，但壓縮與解壓縮需要額外處理時間。在本次 localhost 測試中，RAW 模式的送出端總時間均較短；若未來在低頻寬網路環境下測試，中文或英文文章的 Huffman 傳輸則可能因傳輸量較少而取得優勢，仍需進一步量測驗證。

### 6.4 雙實體電腦 Benchmark 結果與分析

#### 6.4.1 測試環境與方法

為比較 localhost 與實際跨電腦傳輸的效能差異，本研究另外使用兩台 Windows 電腦進行 TCP 傳輸測試。

- **電腦 A（接收端）：** Ethernet 有線網路，IP 為 `192.168.0.140`。
- **電腦 B（傳送端）：** Wi-Fi 無線網路，IP 為 `192.168.0.188`。
- **傳輸模式：** RAW 與 HUFF。
- **測試方式：** 四份檔案各使用 RAW、HUFF 傳輸五次，共 40 次正式測試。

本研究記錄傳送端與接收端的 STATS，並以五次量測的中位數比較效能。原始資料分別保存在 `benchmarks/two_pc_raw_40.csv` 與 `benchmarks/two_pc_medians.csv`。

需要注意的是，雙機中文及英文測試檔案與 localhost 使用的版本在原始大小上略有差異，因此不同環境的耗時結果不適合直接作為純網路成本的比較。

#### 6.4.2 雙機 RAW 與 HUFF 傳輸時間

以下使用傳送端 `total_ms` 的五次量測中位數比較 RAW 與 HUFF 模式。

|---|---:|---:|---:|---|
| 中文文章 | 74.6 ms | 113.2 ms | +38.6 ms | RAW |
| 英文文章 | 136.9 ms | 116.5 ms | −20.4 ms | HUFF |
| 音樂 WAV | 214.7 ms | 3,956.0 ms | +3,741.3 ms | RAW |
| 雜訊 WAV | 136.0 ms | 7,059.5 ms | +6,923.5 ms | RAW |

從測試結果可以觀察到，四份測試檔案中只有英文文章在雙機環境下呈現 HUFF 較快，其餘三份資料均為 RAW 較快。

#### 6.4.3 文字檔案分析

中文文章使用 CHAR Huffman 時，具有明顯的資料壓縮效益，但雙機測試的 HUFF 傳送端總時間為 113.2 ms，高於 RAW 的 74.6 ms，增加約 38.6 ms。

這表示在本次測試條件下，雖然 Huffman 減少了網路傳輸資料量，但整體傳輸時間仍受到編碼、解碼及其他處理成本影響，因此不能僅依壓縮率判定傳輸速度。

英文文章則呈現不同結果：HUFF 的傳送端總時間中位數為 116.5 ms，低於 RAW 的 136.9 ms，減少約 20.4 ms。

此結果顯示，Huffman 在特定檔案與網路條件下可能取得較短的整體完成時間。不過，這是本次五次重複量測得到的實驗結果，尚不足以認定英文文章在所有網路環境下使用 HUFF 都會比較快。

#### 6.4.4 WAV 檔案分析

音樂 WAV 的 HUFF 傳送端總時間為 3,956.0 ms，明顯高於 RAW 的 214.7 ms。

雜訊 WAV 的 HUFF 傳送端總時間為 7,059.5 ms，也遠高於 RAW 的 136.0 ms。

根據本研究的壓縮分析，16-bit PCM WAV 使用 S16 Huffman 時具有大量不同的 Sample 值，使 Codebook 儲存成本增加，甚至造成實際傳輸資料量超過原始檔案大小。

此外，雙機 STATS 也顯示 WAV 在 HUFF 模式下具有較高的編碼處理成本。因此，WAV 的效能劣勢不能單純歸因於網路傳輸時間，而需同時考量編碼計算、Codebook 開銷以及系統執行環境。

#### 6.4.5 localhost 與雙機結果比較

localhost 的 40 次正式測試中，四份檔案皆為 RAW 較快；雙實體電腦的 40 次正式測試中，則只有英文文章呈現 HUFF 較快。

這表示壓縮效益與整體傳輸速度之間並不存在固定關係。即使 Huffman 可以降低上線資料量，是否能縮短完成時間，仍須考量實際網路條件、編解碼成本與系統效能。

此外，由於 localhost 與雙機使用的測試環境不同，且中文與英文檔案版本也略有差異，因此本研究僅比較兩種環境各自的 RAW/HUFF 結果趨勢，不將兩者的耗時差異完全歸因於網路頻寬。

#### 6.4.6 小結

綜合雙機實驗結果，TextLink 在實際跨電腦 TCP 傳輸時，文字檔案可因 Huffman 壓縮減少傳輸資料量，但是否縮短整體時間仍依測試條件而定。

對音樂及雜訊 WAV 而言，S16 Huffman 在本次實驗中不僅增加傳輸資料量，也帶來明顯的編碼時間成本，因此 RAW 模式具有較佳的整體效能。

本次結果進一步說明：**壓縮率較低不一定代表傳輸時間較短，必須同時評估上線 bytes、編解碼時間與端到端完成時間。**


## 7. 損益平衡頻寬分析（Break-even Bandwidth）

本研究除了比較 RAW 與 HUFF 的壓縮比例及實際執行時間，也建立簡化的傳輸時間模型，估計在不同網路頻寬下，Huffman 壓縮是否可能帶來整體時間優勢。

### 7.1 計算方法

假設 RAW 與 HUFF 的共同處理時間相同，Huffman 的編碼與解碼依序執行，且資料傳輸時間可以用上線位元數除以有效頻寬估算：

`T_RAW = T0 + 8 × W_RAW / B`

`T_HUFF = T0 + T_encode + T_decode + 8 × W_HUFF / B`

令兩者總時間相同，可得：

`B_break-even (Mbps) = 0.008 × (W_RAW − W_HUFF) / (T_encode + T_decode)`

其中 W 的單位為 bytes，T 的單位為毫秒（ms）。

本研究以五次正式測試的中位數作為分析依據，並以每輪編碼時間與解碼時間之和的中位數估計 Huffman 額外處理成本。

### 7.2 計算結果與解讀

本研究使用 `benchmarks/formal_raw_40.csv` 的正式量測結果，針對四份測試檔案計算 RAW 與 HUFF 的理論損益平衡頻寬。每種檔案與傳輸模式分別進行五次測試，並使用中位數降低單次量測波動的影響。

本研究以 HUFF 每輪編碼時間（`encode_ms`）與解碼時間（`decode_ms`）之和的中位數，作為簡化模型的額外處理成本。

計算公式：

`B_break-even (Mbps) = 0.008 × (RAW wire bytes − HUFF wire bytes) / 額外編解碼時間 (ms)`

| 測試檔案 | HUFF 節省資料量 (bytes) | 額外編解碼時間 (ms) | 理論損益平衡頻寬 (Mbps) |
|---|---:|---:|---:|
| 中文文章 | 811,687 | 37.60 | 172.70 |
| 英文文章 | 579,537 | 63.00 | 73.59 |
| 音樂 WAV | −299,908 | 283.50 | N/A |
| 雜訊 WAV | −454,822 | 117.50 | N/A |

**中文文章：** HUFF 比 RAW 少傳送 811,687 bytes，額外編解碼時間為 37.60 ms，因此估計損益平衡頻寬約為 172.70 Mbps。在簡化模型下，當有效網路頻寬低於此數值時，Huffman 減少傳輸量所節省的時間可能超過編解碼成本。

**英文文章：** HUFF 比 RAW 少傳送 579,537 bytes，額外編解碼時間為 63.00 ms，估計損益平衡頻寬約為 73.59 Mbps。與中文文章相比，其傳輸量節省較少，且編解碼成本較高，因此損益平衡頻寬較低。

**音樂與雜訊 WAV：** 使用 S16 模式時，HUFF 分別比 RAW 多傳送 299,908 bytes 和 454,822 bytes，同時需要額外的編碼及解碼時間。因此在本研究的簡化模型下，兩者不存在使 HUFF 比 RAW 更快的正損益平衡頻寬，結果以 N/A 表示。

**結果解讀：**

本次結果說明，Huffman 是否能提升整體傳輸速度，取決於壓縮後減少的資料量，以及額外的編解碼成本。在高頻寬環境下，RAW 可能因不需壓縮而更快；在較低頻寬環境下，具有良好壓縮率的文字資料則可能受益於 Huffman。

上述數值是以 localhost 量測的編解碼時間配合簡化頻寬模型推算的理論估計值，並非在不同頻寬下進行的實際端到端測試結果。因此不能直接視為真實網路環境中保證成立的速度分界點。

分析結果：`benchmarks/figures/break_even.csv`。

### 7.3 分析限制

此計算屬於理論模型，並非實際限速網路測得的臨界值。模型未完整考慮 TCP 傳輸行為、網路延遲、封包重傳、磁碟 I/O、系統排程與不同階段可能出現的處理重疊。

因此，計算所得的損益平衡頻寬應作為評估壓縮效益的參考，而非保證實際傳輸速度的門檻。若要驗證模型，未來可在不同實際頻寬限制下，重新測試 RAW 與 HUFF 的端到端完成時間。

## 8. 整體結論

本研究針對 TextLink 專案實作的 Huffman 壓縮功能，使用中文文字、英文文字、音樂 WAV 與雜訊 WAV 四種測試資料，分析不同符號定義下的壓縮效果，並透過 localhost 40 次及雙實體電腦 40 次、合計 80 次正式 Benchmark，比較 RAW 與 HUFF 的傳輸效能。

綜合實驗結果，可以歸納以下結論：

### 8.1 Huffman 壓縮效果取決於資料特性

中文與英文自然語言具有不均勻的符號出現頻率，因此 Huffman 能將常見符號編碼為較短的位元序列，有效減少資料量。

本次中文文章使用 CHAR 模式時，實際上線比例為 **32.39%**；英文文章為 **53.96%**，代表兩者都能顯著降低傳輸資料量。

相較之下，音樂與雜訊 WAV 使用 S16 模式時，實際上線比例分別為 **108.51%** 與 **140.62%**。這表示 Huffman 並非對所有資料都能產生壓縮效益，尤其當符號分布接近均勻時，能夠節省的位元數相當有限。

### 8.2 符號定義會影響壓縮效率

本研究比較了 UTF-8 文字的 CHAR/BYTE，以及 WAV 音訊的 S16/BYTE 兩種符號定義。

中文文章使用 CHAR 模式時，完整編碼比例約為 32.38%，明顯優於 BYTE 模式的 71.66%；英文文章則分別為 53.96% 與 54.21%，差異較小。

在 WAV 測試中，BYTE 模式的完整編碼比例均優於 S16 模式。這是因為 S16 雖然可能產生較短的 Bitstream，但符號種類數量龐大，導致 Codebook 儲存成本顯著增加。

因此，選擇較大的符號單位不代表一定能取得更好的壓縮效果，必須同時考慮資料分布與編碼表大小。

### 8.3 Codebook 與協定開銷不可忽略

本研究發現，純 Bitstream 的壓縮比例與實際上線比例可能存在明顯差異。

例如音樂 WAV 使用 S16 模式時，純 Bitstream 約為原始大小的 95.81%，但加入 Codebook 及其他必要資料後，實際上線比例增加至 108.51%。

雜訊 WAV 的 Codebook 更高達 458,654 bytes，使實際傳輸量增加至原始大小的 140.62%。

短訊息測試也呈現相同現象。由於 TextLink 每則 HUFF 聊天訊息都需建立獨立 Codebook，短訊息的固定開銷容易超過 Bitstream 節省的資料量。

本次測試中，中文與英文自然語言在 2,000 字元時已觀察到傳輸比例低於 100%，而高度重複的字元 A 在 50 字元時就能達到相同條件。

因此，實際壓縮效益不能只看 Huffman 編碼後的位元數，也必須考慮 Codebook、Header 和傳輸協定的額外資料。

### 8.4 壓縮率較好不代表傳輸速度一定更快

在 localhost 的 40 次正式 Benchmark 中，四份檔案的 HUFF 送出端總時間中位數均高於 RAW。

這表示在本次測試環境下，Huffman 所需的額外處理時間，未能被減少傳輸資料量的收益抵銷。

進一步使用編碼與解碼時間建立簡化模型後，中文文章的理論損益平衡頻寬約為 **172.70 Mbps**，英文文章約為 **73.59 Mbps**。

此結果顯示，在較低有效頻寬的網路環境中，具有良好壓縮率的文字資料可能因減少傳輸量而取得速度優勢。

音樂與雜訊 WAV 使用 S16 模式時，不僅編碼後資料量增加，也需要額外編解碼時間，因此在本研究的簡化模型下，不存在使 HUFF 比 RAW 更快的正損益平衡頻寬。

上述頻寬數值皆為模型估計，尚未透過不同頻寬條件下的實際端到端傳輸測試驗證。

### 8.5 研究限制與未來改進方向

本研究除了 localhost 的 40 次正式 Benchmark，也已在兩台實體電腦之間完成 40 次 RAW/HUFF 傳輸量測，並驗證 TXT/WAV 檔案傳輸與 SHA-256 完整性。

然而，兩種環境的測試結果受到網路傳輸條件、電腦效能及測試資料版本等因素影響，不宜將耗時差異完全歸因於網路頻寬。

未來可進一步研究：

1. 在固定頻寬條件下測試，驗證理論損益平衡頻寬是否與實際傳輸結果一致。
2. 加入自動判斷 RAW/HUFF 的機制，避免壓縮後資料量增加。
3. 使用相鄰 PCM Sample 的差值（Delta Encoding）作為 Huffman 符號，以降低音訊資料的熵與 Codebook 開銷。
4. 研究固定 Codebook、Codebook 重複使用或更精簡的符號表示方法。
5. 增加不同類型、長度及複雜程度的測試檔案，提升實驗結果的代表性。

### 8.6 最終結論

本次研究證實，TextLink 所實作的 Huffman 編碼符合 Shannon Entropy 與平均碼長的理論關係，並能在適當的資料條件下有效減少傳輸量。

然而，Huffman 的實際效益受到**符號分布、符號定義、Codebook 大小、資料長度、編解碼時間及網路頻寬**共同影響。

整體而言，Huffman 適合用於具有明顯符號頻率差異且壓縮收益足以抵銷額外成本的資料；對於高熵音訊、短訊息或 Codebook 過大的情況，RAW 可能更有效率。

因此，本研究最重要的結論是：

**「壓縮效果應以實際傳輸資料量與整體效能評估，而非僅以 Huffman Bitstream 大小判斷。」**
